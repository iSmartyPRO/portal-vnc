# PortalVNC Agent Manager — дизайн

## Назначение и зачем

Третий компонент PortalVNC: **графическая утилита администрирования агента**
(`pvnc-admin.exe`). Сейчас всё настраивается вручную — сертификаты через
`provision-certs.ps1`, `config.json` правится в редакторе, служба ставится
скриптами, SID пишутся руками. Менеджер убирает эту возню: через GUI делается
центр сертификации, выпускаются сертификаты, настраивается доступ (IP, SID,
пользователи, группы), управляется служба и виден статус агента.

Утилита **одна** (один exe), но используется в двух местах по роли:
- **на компе администратора** — один раз создаётся единый CA и выпускаются
  сертификаты (агента и операторов);
- **на машинах с агентом** — импорт сертификатов, настройка доступа, управление
  службой, статус.

Та же утилита, перенесённая на настраиваемую машину, работает в режиме настройки
агента. Это соответствует выбранной модели доверия: **единый CA на весь парк**
(вариант A), приватный ключ CA живёт только на компе администратора.

## Цели

- Нативный Windows-exe (C++/Win32), статическая линковка, без рантаймов — как
  остальные компоненты. Переиспользует `pvnc_protocol` и код конфига агента.
- **Центр сертификации (на компе админа):**
  - Создать единый CA (RSA, самоподписанный), ключ CA **зашифрован паролем**,
    хранится в защищённой папке; пароль спрашивается при каждой выдаче.
  - **A-import:** сгенерировать ключ+сертификат агента, подписать своим CA,
    выгрузить бандл (`ca.crt` + `agent.crt` + `agent.key`) для переноса на машину.
  - **A-CSR:** подписать CSR, принесённый с машины агента, вернуть `agent.crt`.
  - Выпустить **клиентский** сертификат (CN=portalvnc-client или именованный)
    для операторов (просмотрщик/портал): бандл `ca.crt` + `client.crt` +
    `client.key`.
  - Генерация ключей и X.509 — через **mbedTLS** (уже в зависимостях), без
    openssl на машине.
- **Настройка агента (на машине агента):**
  - **Статус**: установлена/запущена ли служба, слушается ли порт, версия
    агента, путь к конфигу, список активных подключений.
  - **Сертификаты**: импортировать бандл (разложить в `C:\ProgramData\PortalVNC`,
    прописать пути в `config.json`); либо сгенерировать здесь ключ+CSR для A-CSR.
  - **Доступ**: редактор `allowedClients` (IP/подсети IPv4 CIDR) и
    `access.users` / `access.groups` / `access.sids` через штатный Windows-диалог
    выбора пользователей и групп (DS Object Picker), резолв имён в SID, локальные
    и доменные объекты.
  - **Служба**: установить/удалить/запуск/стоп/рестарт; редактирование `port`,
    `listenAddress`, `trayIcon`, `logFile`.
- Совместимость: читает/пишет существующий формат `config.json`; версия агента
  доступна для проверки совместимости.

## Не-цели (сейчас)

- Удалённое администрирование парка из одного окна (менеджер работает с
  **локальным** агентом машины, на которой запущен; перенос — ногами/копированием
  бандла). Централизованная консоль парка — это веб-портал, отдельно.
- Пер-машинная инфраструктура авто-выдачи/отзыва сертификатов (CRL/OCSP).
  Отзыв — будущая версия; пока отзыв = перегенерация и переустановка.
- Хранение приватного ключа CA на машинах агента (запрещено по модели доверия).
- Управление самим порталом или операторскими рабочими местами.

## Анти-цели (провал, даже если работает)

- Приватный ключ CA оказывается на машине агента или в бандле агента.
- Клиентский приватный ключ оператора попадает на агентские машины.
- Утилита тянет .NET/openssl/иной рантайм.
- Несовместимость с форматом `config.json`, который читает агент.

## Ограничения

- Windows x64, C++17, MSVC, статическая линковка (как agent/viewer).
- Криптография — mbedTLS (RSA keygen, X.509 v3, самоподпись и подпись CSR).
- Служба и конфиг — переиспользуют код агента (`config.*`, имена службы,
  раскладку `C:\ProgramData\PortalVNC`).
- Диалог выбора пользователей/групп — системный **DS Object Picker**
  (`IDsObjectPicker`, `objsel.h`), возвращает имя и SID.
- Иконка — отдельная (из `assets/`), встраивается ресурсом; UI в том же
  премиальном тёмном стиле, что у просмотрщика.

## Архитектура и экраны

Один exe, стартовый экран предлагает роль (или определяет по наличию CA/агента):

### 1. Центр сертификации (Certificate Authority)
- **CA**: создать новый CA (имя, срок, размер ключа) → ключ шифруется паролем.
  Важно: у mbedTLS нет записи зашифрованного приватного ключа (только чтение),
  поэтому используем **собственный контейнер**: приватный ключ выписывается в PEM
  в память, затем шифруется **AES-256-GCM** с ключом из **PBKDF2** (`MBEDTLS_PKCS5_C`,
  соль+итерации в заголовке контейнера), плейнтекст в памяти затирается. Файл —
  не стандартный `.key` (читается только нашей утилитой). Хранится в защищённой
  папке профиля администратора (напр. `%LOCALAPPDATA%\PortalVNC\CA`, ACL —
  только текущий пользователь). Рядом — счётчик серийных номеров. Открыть
  существующий CA (ввод пароля). Показать отпечаток/срок.
- **Выпустить сертификат агента (A-import)**: ввести CN/идентификатор машины →
  сгенерировать ключ агента + подписать CA → сохранить бандл (zip или папка):
  `ca.crt`, `agent.crt`, `agent.key`.
- **Подписать CSR (A-CSR)**: выбрать `.csr` с машины → подписать CA → сохранить
  `agent.crt` (+ `ca.crt`).
- **Выпустить клиентский сертификат**: CN оператора → бандл `ca.crt`,
  `client.crt`, `client.key`.

### 2. Настройка агента (Agent setup)
- **Статус** (без сертификатов): читает службу через SCM (установлена/состояние),
  проверяет порт, читает **версию из exe агента** (version-ресурс) и
  **`status.json`**, который пишет агент (версия, запуск, активные подключения).
- **Сертификаты**: импорт бандла → копировать в `C:\ProgramData\PortalVNC`,
  обновить `config.json` (`tls.ca/cert/key`). Либо «Сгенерировать ключ+CSR» →
  сохранить `agent.key` локально и `agent.csr` для переноса к админу.
- **Доступ**: таблицы `allowedClients`, `access.groups/users/sids`; кнопки
  «Добавить пользователя/группу» открывают системный object picker (ограничен
  пользователями и группами). **Выбор из picker сохраняется как SID в
  `access.sids`** (устойчиво к переименованию и работает при недоступном домене),
  а в UI отображается человекочитаемое имя, разрешённое из SID. Ручной ввод имени
  пишется в `access.users`/`access.groups` (как и раньше), ручной ввод IP/CIDR —
  **только IPv4** (агент матчит только IPv4/CIDR; IPv6 редактор отклоняет). Всё
  пишется в `config.json`.
- **Служба**: install/uninstall/start/stop/restart; поля `port`,
  `listenAddress`, `trayIcon`, `logFile`.

## Необходимые доработки в агенте

- **Версия в exe**: добавить ресурс `VS_VERSION_INFO` в `pvnc-agent.exe` (сейчас
  `pvnc_agent.rc` содержит только иконку), значение версии подаётся из CMake.
  Менеджер читает версию через `GetFileVersionInfo` из exe агента (работает без
  запущенного агента). Дополнительно версия агента отдаётся по control-каналу
  **отдельным полем `agentVersion`** в `SysInfo` — не путать с `os.version` (это
  сборка Windows); существующий разбор в `viewer/src/sysinfo_dialog.cpp` не
  ломается (поле новое).
- **Реестр активных сессий в агенте**: сейчас соединения обрабатываются в
  detached-потоках (`rfb_server.cpp`) без общего списка, а имя пользователя
  затирается сразу после входа (`hs.creds.wipe()`). Нужно добавить потокобезопасный
  список сессий в `RfbServer`: регистрировать при успешном входе
  `{user, ip, mode(Screen/Control), since}` (имя сохранить ДО `wipe`), снимать при
  выходе потока; под мьютексом.
- **`status.json` при мультипроцессной модели**: служба — супервизор в session 0,
  запускает по одному **рабочему процессу на сессию** на разных портах
  (`base`/`base+sessionId`). Поэтому **каждый рабочий пишет свой файл**
  `C:\ProgramData\PortalVNC\status-<port>.json` — `{agentVersion, startedAt, port,
  sessions: [{user, ip, since, mode}]}` (из своего реестра сессий, период ~5 с,
  ACL: Администраторы/SYSTEM). Менеджер читает и **агрегирует все `status-*.json`**.
  Живой опрос по control-каналу остаётся для портала/удалённо.

## Переиспользование кода агента и упаковка

- **Запись конфига.** В агенте есть только чтение (`parseConfig` кладёт в
  фиксированную структуру и теряет незнакомые ключи). Менеджер **не делает
  round-trip через структуру** — он правит «живое» JSON-дерево (`nlohmann::json`:
  загрузить файл, изменить нужные ключи, записать обратно), сохраняя незнакомые/
  будущие поля.
- **Служба.** `installService()` сейчас вшита в exe агента, печатает в stderr и
  жёстко берёт путь к своему exe. Нужно **вынести в общий модуль** install/
  uninstall с параметром «путь к exe службы», плюс добавить start/stop/restart/
  query-state (SCM). Агент (`--install`) и менеджер используют этот модуль.
- **Где найти установленный агент.** Менеджер — отдельный exe. Он читает путь к
  агенту из **ImagePath службы** (`QueryServiceConfig`), оттуда выводит папку
  конфига; запасной путь — `C:\ProgramData\PortalVNC`.
- **Упаковка.** `pvnc-admin.exe` — **портативный standalone exe** (без MSI):
  роль «Центр сертификации» работает на компе админа, где агента/MSI нет вовсе,
  а «перенос ногами» на машины — копированием exe. Отдельная сборка (таргет
  `admin/`), RC-язык уже включён в корневом CMake. Иконка — своя из `assets/`.

## Модель безопасности

- Приватный ключ CA — только на компе администратора, **зашифрован паролем**,
  в папке профиля с ограниченными правами. В бандлы агента и клиента **не
  попадает** (кладётся только публичный `ca.crt`).
- Бандл агента содержит приватный ключ агента — передаётся на машину
  администратором; кладётся в `C:\ProgramData\PortalVNC` с правами
  Администраторы/SYSTEM.
- Клиентский приватный ключ — только у оператора; на агентские машины не кладётся.
- A-CSR предпочтителен: приватный ключ агента генерируется и остаётся на машине,
  наружу уходит только CSR.
- **CN сертификатов сейчас косметический.** Агент авторизует оператора по учётной
  записи Windows + SID (`AccessPolicy`), а TLS лишь проверяет, что сертификат
  подписан нашим CA; CN пира читается, но в авторизации **не участвует**. То есть
  любой сертификат, подписанный нашим CA, равнозначен. Именованные клиентские
  сертификаты нужны для учёта/будущего пер-операторского отзыва, но **не являются
  точкой контроля доступа** в текущей версии (проверка CN-списка на агенте —
  будущая возможность, не цель сейчас).

## Что оставлено строителю

- Формат бандла (папка vs zip) и способ переноса.
- Точные параметры PBKDF2 (итерации, размер соли) и формат заголовка контейнера
  ключа CA.
- Профили расширений X.509 — переиспользовать из `provision-certs.ps1` (CA:
  CA:TRUE + keyCertSign/cRLSign; leaf: CA:FALSE + digitalSignature/keyEncipherment
  + EKU serverAuth,clientAuth).
- Раскладка экранов/вкладок и детали UI (в премиальном тёмном стиле, своя иконка).
- Флаги области object picker (`DSOP_SCOPE_*`: локальная машина / домен /
  доверенные домены) — разумные значения по умолчанию.
- Эвристика авто-определения роли (наличие папки CA / установленной службы).
- Затирание буферов приватных ключей в памяти и ACL на файлы ключей
  (SYSTEM/Администраторы) — обязательная гигиена, детали на усмотрение строителя.
