# PortalVNC — дизайн

## Назначение и зачем

PortalVNC — средство интерактивного удалённого доступа к Windows-компьютерам,
аналог VNC, но с улучшенными возможностями под задачи администрирования парка
машин в доменной и бездоменной среде.

Главная проблема, которую решаем: подключаться к машинам должны **администраторы
компьютера независимо от языка Windows** (английская, русская, турецкая и т.п.).
Поэтому доступ определяется не по имени группы, а по SID локальной группы
«Администраторы» (`S-1-5-32-544`) — это работает одинаково на любой локали.
Доменные администраторы покрываются автоматически: `Domain Admins` по умолчанию
входят в локальную группу «Администраторы» целевой машины.

Инструмент должен быть лёгким и мало зависеть от окружения: никаких
дополнительных фреймворков (.NET и т.п.), нативные исполняемые файлы со
статической линковкой. Рядом с каждым компонентом — минимум файлов (ориентир:
до 5 библиотек, если нужны). Подключение — защищённое, шифрованное.

PortalVNC встраивается в уже существующий модуль `remote` веб-портала
(docker-app-skeleton, репозиторий `/dockers/portal`). В портале уже готовы:
каталог компьютеров из AD, журнал подключений, права, менеджер паролей, а также
туннель `браузер → WebSocket → guacd → RDP/VNC/SSH`.

Важно: PortalVNC **не использует guacd**. guacd остаётся только для RDP/VNC/SSH.
У PortalVNC своя обвязка — собственный шлюз между браузером и агентом, —
незаметно подключённая в тот же интерфейс Remote Control (тот же каталог,
журнал, менеджер паролей). Для пользователя это выглядит как ещё один способ
подключения внутри знакомого модуля.

## Цели

- Один нативный Windows-exe на агент, без рантаймов, со статической линковкой.
- Доступ членам локальной группы «Администраторы» по SID, независимо от локали
  Windows; возможность добавить другие SID (например, доменную группу helpdesk).
- Аутентификация учётной записью Windows (пароль проверяет сама ОС), без
  собственного хранилища паролей.
- Шифрованный канал с взаимной проверкой сертификатов (mTLS): к агенту
  подключается только носитель сертификата от нашего CA (наш клиент и шлюз
  портала), посторонний VNC-клиент подключиться не может.
- Три компонента в одном Git-репозитории, собираемые сразу: агент (сервер),
  клиент-просмотрщик, библиотека для портала.
- Общий модуль протокола с версионностью и согласованием возможностей;
  несовместимые версии получают понятный отказ.
- Структура по папкам, семантическое версионирование каждого компонента,
  готовность к переиспользованию в разных проектах.
- Работа на экране блокировки и в окнах UAC (режим службы).
- Несколько операторов одновременно на одной машине (один кадровый поток на всех).
- Подключение к терминальному серверу без активной консольной сессии (в объёме
  с первого релиза; это самая тяжёлая часть — выбор целевой сессии и захват в
  пользовательской сессии через вспомогательный процесс).
- Подключение «без хлопот»: пользователь портала открывает компьютер и сразу
  видит экран; выбор транспорта, учётных данных и целевой сессии делается за
  кулисами.

## Не-цели (сейчас)

- Агенты под не-Windows ОС. LibVNC выбран с прицелом на будущую переносимость,
  но сейчас реализуется только Windows-агент.
- Смена настроек агента «на лету» из портала. `config.json` правит только
  администратор или GPO (локальный файл в защищённой папке).
- Передача файлов, печать, проброс звука, RemoteApp на уровне агента (портал даёт
  RemoteApp через RDP/guacd отдельно; в PortalVNC это не входит).
- Собственное хранилище учётных данных (используется менеджер паролей портала).

## Анти-цели (что считаем провалом, даже если технически работает)

- Зависимость агента от установленного .NET или иного рантайма.
- Доступ по имени группы вместо SID (ломается на не-английской Windows).
- Канал, к которому может подключиться произвольный публичный VNC-клиент.
- Разрастание на десятки файлов рядом с exe.
- Невозможность собрать проект по этому документу без обращения к заказчику.

## Ограничения

- Целевая ОС агента: Windows 10/11 и Windows Server (x64).
- Язык: C++ (C++17 или новее), сборка со статической линковкой зависимостей.
  На выходе — минимальное число файлов рядом с каждым exe.
- Зависимости (ориентир, до ~5 на компонент): LibVNC (libvncserver/libvncclient),
  TLS-библиотека (OpenSSL или совместимая), zlib, libjpeg-turbo. Все линкуются
  статически.
- Лицензия: LibVNC под GPL. Репозиторий и агент распространяются под GPL;
  это зафиксировать в LICENSE репозитория.
- Портал: модуль `remote` построен на `guacamole-lite` + `guacd` для RDP/VNC/SSH.
  PortalVNC к guacd не подключается — у него собственный шлюз (см. ниже),
  встроенный в тот же модуль `remote`. Потребуются аккуратные добавления в модуль
  `remote` портала: новый тип хоста (`portalvnc`), маршрут на наш шлюз, пункт в
  интерфейсе Remote Control. Существующий туннель к guacd не трогается.
- Конфигурация агента — `config.json` рядом с exe, в защищённой папке
  (Program Files). Служба читает его при старте и перечитывает при изменении.

## Архитектура

Три компонента + общий модуль протокола, один репозиторий:

```
┌────────────────────┐   mTLS / наш протокол   ┌────────────────────┐
│  Клиент-просмотрщик │ ◄─────────────────────► │   Агент (служба)    │
│  (Windows, C++)     │                         │   на целевой машине │
└────────────────────┘                         │  - захват DXGI/GDI  │
                                                │  - ввод             │
┌────────────────────┐                         │  - SID-проверка     │
│  Браузер (viewer в  │   WebSocket (wss)       │  - config.json      │
│  модуле Remote      │ ◄───────────┐           │  - значок в трее    │
│  Control портала)   │             │           │  - выбор сессии     │
└────────────────────┘             ▼           └────────────────────┘
                        ┌────────────────────┐            ▲
                        │  Шлюз PortalVNC     │  mTLS /    │
                        │  (библиотека для    │  наш       │
                        │   портала, sidecar) │────────────┘
                        └────────────────────┘
```

guacd в этой схеме не участвует — он остаётся для RDP/VNC/SSH отдельно.

### 1. Агент (сервер)

- Windows-служба, автозапуск. Один exe + `config.json` + файлы TLS.
- Значок «сетевой компьютер» в системном трее у вошедшего пользователя —
  опционально, управляется `config.json`, **по умолчанию выключен** (фоновый режим).
- Захват экрана: DXGI Desktop Duplication для обычного рабочего стола. Важно: на
  экране блокировки, на Secure Desktop и в session 0 DXGI недоступен, поэтому
  второй путь захвата (кандидат — GDI `BitBlt`) здесь не запасной, а основной для
  ключевой возможности «работа на экране блокировки и в UAC». Строитель
  реализует оба и переключается по доступности.
- Ввод: клавиатура, мышь, работа на экране блокировки и в окнах UAC. Служба в
  session 0 запускает вспомогательный процесс в целевой пользовательской сессии
  (и на Secure Desktop), который и делает захват и ввод; служба и помощник
  общаются через IPC. Конкретный механизм IPC — на усмотрение строителя.
- Выбор целевой сессии: на терминальном сервере активных сессий несколько, на
  рабочей станции может не быть ни одной активной консольной. Агент перечисляет
  сессии (WTS API) и выбирает целевую (по умолчанию консольная; для терминального
  сервера — по имени пользователя из рукопожатия или явному выбору). Для каждой
  обслуживаемой сессии поднимается свой вспомогательный процесс.
- Аутентификация: после mTLS клиент передаёт имя пользователя и пароль Windows;
  агент проверяет их через `LogonUser`/SSPI средствами ОС, затем проверяет, что
  в токене есть SID `S-1-5-32-544` (или иной SID из `config.json`). Своих паролей
  не хранит.
- Несколько операторов одновременно: один захваченный кадровый поток рассылается
  всем подключённым; ввод от каждого применяется, конфликт — «последний ввод
  побеждает».
- Локальный журнал подключений (`logFile` из конфига): кто, когда, с какого IP,
  результат.

### 2. Клиент-просмотрщик

- Отдельный Windows-exe. Говорит только на нашем протоколе (mTLS + наше
  рукопожатие), с обычным VNC-сервером не совместим намеренно.
- На базе LibVNC (libvncclient) + наш слой TLS и рукопожатия.
- Рисует экран, передаёт клавиатуру/мышь. Интерфейс минимальный.

### 3. Библиотека для портала (шлюз PortalVNC + браузерный просмотрщик)

Это и есть «отдельная обвязка» PortalVNC, минующая guacd. Состоит из трёх частей:

- **Шлюз (sidecar).** Отдельный процесс рядом с порталом (как guacd — отдельный
  контейнер). Со стороны браузера принимает WebSocket (wss), авторизованный
  существующим механизмом сессий/токенов портала. Со стороны агента открывает
  наше mTLS-соединение, проводит рукопожатие (версия, capabilities, учётные
  данные Windows, взятые из менеджера паролей портала) и пересылает кадры и ввод.
  Шлюз держит клиентский сертификат нашего CA — именно он делает портал доверенным
  клиентом для агента. Язык/рантайм шлюза — на усмотрение строителя (кандидаты:
  небольшой нативный процесс или Node), но он относится к репозиторию PortalVNC,
  а не к порталу.
- **Браузерный просмотрщик.** JS-компонент в модуле `remote` портала: рисует
  кадры на `<canvas>` и передаёт клавиатуру/мышь, общаясь со шлюзом по WebSocket.
  Поскольку полезная нагрузка внутри — RFB, кандидат — адаптировать noVNC
  (`RFB.js`): шлюз отдаёт браузеру обычный RFB-over-WS, сняв наш mTLS и
  рукопожатие на своей стороне. Интерфейс вокруг — наш, в стиле портала.
- **Привязка к модулю `remote`.** Небольшие добавления в портал: тип хоста
  `portalvnc`, маршрут на шлюз, пункт подключения в интерфейсе Remote Control.
  Для пользователя — тот же модуль; маршрутизация на guacd или на наш шлюз
  выбирается по типу хоста незаметно.

### Общий модуль протокола (shared)

- Одна внутренняя библиотека, используемая всеми тремя компонентами.
- Отвечает за: установление mTLS, формат рукопожатия, обмен версиями протокола и
  согласование возможностей (capabilities). При несовпадении версий —
  структурированный отказ с понятным кодом/сообщением.
- Имеет собственную семантическую версию, отдельную от версий компонентов.

**Форма протокола (решение дизайна):** TLS оборачивает всё соединение целиком
(TLS-туннель поверх TCP). Внутри туннеля сначала идёт наше короткое рукопожатие
(версия протокола + capabilities + имя пользователя/пароль Windows), затем —
обычный RFB-поток. Следствие: стоковый VNC-клиент наш канал напрямую не
понимает — нужен наш просмотрщик или шлюз портала, снимающий TLS и рукопожатие.
Это намеренно: именно так посторонний
VNC-клиент и отсекается. Выбор TLS-библиотеки — OpenSSL 3.x (лицензия
Apache-2.0, совместима с GPL) как кандидат; строитель может заменить на mbedTLS.

## Безопасность и доступ

- **Транспорт:** TLS с взаимной проверкой сертификатов. Агент доверяет только
  клиентам с сертификатом, подписанным нашим CA. CA, сертификат агента и путь к
  ним задаются в `config.json`.
- **Модель сертификатов (первая версия):** один общий сертификат агента на весь
  парк машин — задача первой версии только зашифровать канал и отсечь чужих
  клиентов. Отдельные сертификаты на каждую машину (и возможность отозвать одну
  скомпрометированную) — будущая версия, когда появится собственный CA. Формат
  `config.json` уже предусматривает путь к сертификату на машину, поэтому переход
  на пер-машинные сертификаты не ломает схему.
- **Сетевой фильтр:** `allowedClients` в `config.json` — список IP/подсетей, с
  которых разрешено подключение (аналог `AuthHosts` UltraVNC). По умолчанию —
  только явно заданные адреса (например, шлюз портала).
- **Аутентификация пользователя:** учётная запись Windows через ОС; авторизация —
  членство в группе по SID.
- **Прозрачность:** значок в трее управляется конфигом, по умолчанию выключен
  (режим unattended для парка машин компании). Запрос согласия на подключение не
  выводится. Примечание: «тихий» режим — осознанное решение заказчика для машин,
  принадлежащих компании; политику его применения компания фиксирует отдельно,
  на архитектуру это не влияет.

## config.json (агент)

Лежит рядом с exe в защищённой папке; правит администратор или GPO. Параметры,
которых нет в файле, принимают безопасные значения по умолчанию.

| Ключ | Назначение | По умолчанию |
|---|---|---|
| `trayIcon` | Показывать значок в трее | `false` |
| `listenAddress` | Адрес прослушивания | все интерфейсы |
| `port` | Порт | `7654` |
| `tls.cert` | Сертификат агента | — |
| `tls.key` | Ключ агента | — |
| `tls.ca` | Доверенный CA (для mTLS) | — |
| `allowedClients` | Разрешённые IP/подсети | пусто → никто (нужно задать) |
| `access.sids` | Доп. SID, которым разрешён доступ | `S-1-5-32-544` |
| `logFile` | Путь к локальному журналу | рядом с exe |

## Версионность и структура репозитория

- Папки по компонентам: агент, клиент, библиотека для портала, общий модуль
  протокола. Конкретные имена папок — на усмотрение строителя, но разделение
  строгое.
- Каждый компонент — своя семантическая версия; общий модуль протокола — своя.
- Проверка совместимости выполняется в рукопожатии по версии протокола, не по
  версиям компонентов.
- Git с самого начала; LICENSE (GPL); README с картой репозитория и порядком
  сборки.

### Установка агента

- **MSI-установщик** — основной способ: кладёт exe, `config.json`, сертификаты и
  CA, правило брандмауэра (порт 7654 только с заданных адресов), регистрирует
  службу. Раскатывается через GPO (назначение MSI на OU) и ставится вручную
  двойным кликом — оба сценария из одного пакета.
- Также допустим **портативный вариант** (zip/exe + скрипт регистрации службы)
  для ручной установки там, где GPO не используется.
- Портал может показывать статус установки на машине (стоит ли служба, отвечает
  ли порт) — проба со стороны шлюза PortalVNC.

## Что оставлено строителю

- Точный механизм IPC между службой (session 0) и вспомогательным процессом в
  пользовательской сессии / на Secure Desktop.
- Система сборки (CMake как кандидат) и тулчейн (MSVC, vcpkg/ручные зависимости).
- Точные имена папок и раскладка внутри репозитория.
- Рантайм шлюза PortalVNC (нативный процесс или Node) и формат WebSocket между
  браузером и шлюзом (кандидат — RFB-over-WS под noVNC `RFB.js`).
- Формат wire-протокола поверх базового RFB (какие расширения/capabilities нужны
  сверх RFB) и формат структурированного отказа при несовместимости версий.
- Конкретная проба статуса установки со стороны шлюза.
